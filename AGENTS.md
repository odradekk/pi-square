# pi-square Agent Guide

## Project Overview

- **Name:** `pi-square` (pi-squared).
- **Language:** TypeScript using ECMAScript modules. Tests and supporting scripts also use JavaScript ESM.
- **Purpose:** A unified local extension package for the Pi coding agent. It provides prompt management, interactive and session tools, local text and file search, persistent SSH shells, web search and fetch, library documentation tools, subagents, TUI customizations, PowerShell execution, and themes.
- **Built on:** Node.js 24, Pi 0.84.2, the Pi extension API, Pi TUI and AI packages, and TypeBox. The public npm package is loaded by Pi directly from `src/index.ts`.

## Architecture

- `src/index.ts` is the single extension entry point. It loads configuration on session start and registers each feature module.
- `src/core/` owns shared configuration, diagnostics, path handling, and the session-scoped FIFO confirmation coordinator. `src/core/safe-write.ts` owns the shared safe-file-write primitives — identity-tracked locks with stale reclaim, dev/ino/birthtime file identity, same-node unlink, and fsync'd exclusive temporary files — consumed by the display configuration writer (the former Shadow Minds overlay writer was its second consumer until #190 removed it); callers keep their own error types and codes through a fail factory. Strict configuration V2 merges agent-level `config/pi-square.json` with project-level `.pi/config/pi-square.json`; V1 and the former SSH `confirmCommands` field are rejected with migration diagnostics. SSH profiles and anchored editing are security-sensitive agent-only settings and are rejected in the project layer rather than merged.

## Rules and Constraints

- Preserve the Node.js 24 and Pi 0.84.2 runtime contract unless the change explicitly updates compatibility and documentation.
- Keep the project ESM-only and compatible with the strict settings in `tsconfig.json`, including unused-symbol checks and no emitted JavaScript.
- Register extension behavior through `src/index.ts`. The package exports only `.`, the intentional declarative `./display` integration API, and `./package.json`; do not add other package entry points or deep-import contracts without an explicit architecture change.
- Validate external configuration and tool inputs at their boundaries. Reject unknown or invalid configuration rather than relying on unchecked values internally.
- Keep every model-callable tool parameter schema provider-compatible: use a strict top-level `Type.Object` with `additionalProperties: false`; never use top-level `Type.Union`, `anyOf`, or `oneOf`. Represent operation or mode branches with a required `StringEnum`, enforce branch-specific field combinations at execution validation, and add contract coverage for the top-level object shape, absent unions, and required discriminator. Split a branch into its own tool when a branch-specific field must not appear in sibling branches at all: models served through the OpenAI Responses API populate every declared schema property, so a field that sibling modes reject (such as the resume-only `id`) would make the shared schema unusable for them. This is why subagents expose `delegate_subagent` (task) and `resume_subagent` (id/task) as separate tools; their execution validation also treats blank optional strings as unset.
- Keep non-secret settings in agent-level `config/pi-square.json` or project-level `.pi/config/pi-square.json`. SSH profiles and both `anchoredEditing` settings (`enabled` and `autoRead`) are agent-only; project layers that contain `ssh` or `anchoredEditing` are rejected atomically. Display policy precedence is fixed as package defaults, agent defaults/family/tool, then project defaults/family/tool, so project scope wins over all agent specificity. `/display` writes must retain canonical-scope, lock/CAS, symlink/identity, complete-candidate validation, mode-preservation, atomic-rename, stale-review, and project-trust guarantees. `footer.mode` remains only a deprecated accepted layer input with no runtime effect until reviewed removal. Credentials and model definitions belong to Pi-owned `auth.json` and `models.json`; never commit secrets.
- Keep the bundled role catalog to three visible complementary profiles: Explorer for local evidence, Crawler for focused web and Context7 research, and Generalist for scoped writable work. The hidden `example_profile` reference definition stays non-visible. Agent and project overlays may define roles with any name, including the retired `oracle` and `librarian`; a definition that requests a retired extension tool fails through the ordinary unsupported-tool contract (ADR-0015). Package profiles omit model and effort so fresh runs inherit the parent values; same-ID resume keeps the original frozen values. All profiles inherit the parent system. Every bundled specialist disables discovered skills, while Generalist receives the explicit tool set and all discovered skills.
- Preserve explicit tool-list semantics: omitted or empty `tools` selects runtime defaults, the exclusive `tools: [none]` sentinel selects no built-in tools, and extension tools remain opt-in. Persist the logical selection so resume re-resolves platform capabilities without silently broadening access.
- Preserve feature ownership and avoid unrelated refactors. Add shared abstractions only when multiple modules have a demonstrated common requirement.
- Keep model-callable shell tools platform-exclusive: non-Windows sessions expose bash only, Windows sessions expose pwsh only, and subagents request the portable `shell` capability rather than declaring both names. Parent non-Windows bash is registered only by `src/display/builtins.ts`; `src/shell/` registers only Windows pwsh and platform call guards.
- Keep the fixed visual grammar in code, not in configuration. The shipped grammar is the calm operational display: one `●` marks every tool entry on a color-capable terminal, color carries lifecycle through existing semantic tokens, and a distinguishable one-cell fallback glyph set replaces color when the runtime reports no color. Only the running marker may animate: in full-motion color sessions it breathes over a 1.6 s period through accent brightness (never disappearing); reduced, off, CI, non-TTY, dumb-terminal, and no-color sessions keep it static. The scheduler drives duration and pulse updates at 120 ms for `full`, duration-only updates at 1 s for `reduced`, and no timer for `off`. The `family` field stays in the catalog and keeps selecting the owning adapter; it does not select a glyph. The title carries the tool identity; no family icon is rendered. Titles are sentence case and unique within each family (`Grep` versus `Text search`). The title keeps its natural width with a single space before the target at every tier. The header is always exactly one row and carries marker, title, target, inline outcome (or one-sentence failure), and elapsed duration; a long target is truncated with `…` and never wraps, and a path target follows C2 (workspace-relative, `~` under the home directory, middle elision that never loses the file name). Qualifiers never render header badges; renderer-side clipping is stated once at the end of the body as `⋯ +N ...`. Compact layouts drop the duration first. A collapsed entry is exactly one row; running and queued entries never stream a live tail into the collapsed view. The mutation family (`edit`, `insert`, `replace`, `write`) is the only exception: `edit` and `write` keep a bounded preview/diff evidence body below the row, while the anchored mutations `replace` and `insert` render only their authoritative unified diff body in collapsed and expanded success states. Payloads of every other tool (command output, search results, subagent reports, and so on) are visible only when the entry is expanded. Expanded bodies are evidence views: they use a shared two-cell indent without tree rails, do not repeat the header outcome, prune sections that only restate the header, and render explicitly enabled metadata as one bounded muted row. Row drop order is fixed: duration, then the inline summary (eliding before dropping), then target truncation; the one-row guarantee and the no-trailing-empty-row rule are preserved. In the wide layout tier (viewport of 100 columns or more) entries render at 60 percent of the viewport width, minimum 60 cells, left-aligned, and expanded entries keep the same column so expansion never causes horizontal jumps; below the wide tier entries keep full width. The content column applies uniformly to header, body, sections, preview, and diff. Hue carries two levels (see [ADR 0012](docs/adr/0012-self-defined-calm-palette.md)): the state marker (lifecycle) and diff added/removed lines carry semantic state tokens, tool titles carry the `toolTitle` identity token, and targets, inline summaries, and body text stay muted or neutral. Nothing is colored for decoration and no row background is tinted by its outcome. Both bundled themes are a warm-neutral pair sharing a hue skeleton but calibrated independently against their own backgrounds; they must clear the palette gates in ADR 0012. Token structure, token names, and var-alias indirection stay unchanged so markdown, syntax, thinking-level, and bash-mode colors continue to resolve. A failure states one human sentence in the header, and the raw platform text appears exactly once, in an expanded `Error` evidence section. Visual acceptance must assert the bullet marker, fallback glyph set, running-pulse downgrade behavior, marker widths, the one-row header, natural single-space title spacing, the absence of qualifier badges, the one-row collapsed entry, the mutation-family body rules including the anchored tools' diff-only body, the wide-tier content column, the absence of family icons and tree rails, and the two-level hue tones through the production decoration path rather than through synthetic descriptions alone.
- Keep the shared operational display declarative and theme-portable. All parent tools and pi-square-owned TUI surfaces use `src/display/` sanitization, budgets, standard semantic theme tokens, responsive boundaries, and the one session-owned scheduler at 120 ms intervals (`full`), 1 s intervals (`reduced`), or static (`off`). Runtime-independent tool definitions remain renderer-free; parent registrars apply the owning declarative adapter, production tests exercise those decorated definitions, and a result must visually replace the pending call rather than render as a second operational entry. Expanded results use the closed internal `DisplaySection` model from `src/display/types.ts`; public Adapter v1 remains limited to its published field kinds and does not accept internal sections. Background subagent completion messages are the explicit native-shell exception. Tests, CI, non-TTY, and incapable environments downgrade deterministically. Do not patch ordinary user/assistant message components, introduce a second required palette, retain native/legacy renderer branches, or let child tool construction require a parent display runtime.
- Keep Pi built-in overrides factory-faithful and ownership-aware. Recreate `read`, `grep`, `find`, `ls`, `edit`, `write`, and non-Windows `bash` only from Pi 0.84.2 public factories and spread the original definition. Ordinary built-ins replace renderer fields only. The declared anchored exceptions are `read`'s conditional guard and post-factory model-visible content transform, plus `write`'s narrow execution-context wrapper and injected filesystem operations described below; no other execution or model-content wrapper is allowed. Every anchored operation takes the per-target cross-process exclusion (`src/anchored-edit/file-lock.ts`) through the operation boundary (#264), and one canonical target flows through queue key, lock, byte read/validation, filesystem commit, and store publication — reads and replaces resolve it at the boundary, while the shared parent/child execution wrapper resolves the final factory argument once immediately before Pi registers its queue; anchored write definitions are sequential and completed outcomes are keyed by immutable tool-call ID, so identical calls and later middleware argument rewrites cannot overwrite or consume one another's result; a symlink retargeted mid-operation or mid-queue cannot redirect the locked target or strand the appendix; anchored reads hold it from reading file bytes through committing the matching snapshot and served hashes, and every mutation — `replace`, the parent and child `insert` (#285, #287), the parent write, and the child anchored `write` — uses Pi's per-file mutation queue as the outer in-process serializer and the anchored lock as the inner serializer (the writes join through the public write factory's injected filesystem-operation seam; the ADR-0007 lock-order inversion is superseded by ADR-0014). The lock files live under `anchored-edit/locks/` beside the store and are keyed by the SHA-256 of the operation key — the canonical target path, or the file's stable dev/ino identity for an already-existing multi-link file so its hard-link aliases coordinate — including external targets, whose locks stay in the initiating workspace's lock area (#185); parallel edits to different files never contend. Ownership is a complete atomic record (random token, a pid within the representable OS range, host, and a strictly-digits Linux process start time) published by exclusive-temp-plus-hard-link with no writable fallback — publication failure outside the held case propagates fail-closed, and only complete records are attributable (malformed, pre-token, non-numeric-start-time, and out-of-range-pid records are waited on, never reclaimed; through the liveness probe, only ESRCH proves death while every unexpected probe error fails closed). Removal is a marker-guarded verified protocol that never renames the canonical lock path away before proving, under a per-target removal marker, that the file to remove is still the exact one the remover verified (node identity plus unique acquisition token; inode reuse inside one coarse birthtime window can falsify identity alone). While a marker is held no other remover can act, and the occupied canonical path prevents a successor from installing before the single verified rename-take; afterward the remover deletes only the retired exact file, so a newly installed successor is untouched; a stale verifier that finds a successor's token walks away having touched nothing, so the canonical path is never emptied behind a live successor and a third writer can never slip in. A marker whose holder died is reclaimed through a per-dead-token claim: reclaimers must first win an exclusive fixed-length claim file derived from the dead marker's unique token, and only the claim winner ever takes the marker path — two stale reclaimers can never race a check-then-rename on the marker itself, and a live marker installed by another reclaimer (or a fresh remover that won the take-to-publish gap) is never displaced. A claim holder that crashed between publishing its claim and taking the marker is recovered under a guard derived from that claim's unique token; the guard covers the final read and take, competing stale reclaimers cannot displace a successor, and recursively dead guards fail closed at a fixed depth bound. A live marker makes acquisition busy and bounded; when releasing a record owned by the live process, that marker supplies remover exclusion for exact self-removal so the operation never carries its lock forward. All removal and marker waits share the calling acquire's deadline and cancellation and end in the classified `E_FILE_LOCKED` outcome; a release-time removal runs under its own bounded budget and only logs on failure. A lock held by a confirmed-live or unverifiable owner (foreign host, reused pid, malformed record) is never reclaimed because time elapsed, while a crashed local owner is reclaimed only on a positive death determination (a start-time mismatch proving pid reuse, or an OS-confirmed dead pid; an unreadable start time falls back to the liveness probe). A bounded wait or cancellation in reads, inserts, replaces, and parent or child writes ends in `[E_FILE_LOCKED]` with nothing modified. A post-commit abort is repaired to truthful success from the exact call-ID outcome. `[E_RANGE_STALE]` is reserved for post-lock validation against a file that no longer matches the served range and keeps returning the current range with fresh anchors. Authorization is version-bound (#264 review): every served row records the checksum of the exact content version it was served for, a replace may verify only rows recorded for the file's current version, and rows for any other version authorize nothing for any owner — the parent included — so an external modification, a failed post-commit publication, or a crash at that boundary invalidates the previous authorization until a fresh read; the refusal's feedback rows are published version-bound from inside the boundary so the model's immediate retry verifies. Post-commit failures stay truthful and never authorize stale anchors: a replace whose publication fails keeps the success, suppresses fresh anchors, and warns with `[E_STATE_UNAVAILABLE]`; an anchored write's state publication is one repository transaction (`publishWrite`) that replaces the previous served rows for exactly the written content version, and any failure rolls the whole transaction back — the previous version's rows remain, are stale against the written bytes, and refuse every old anchor (unchanged rows included) until a fresh read, while the write result keeps its truthful success with a unified bounded `[E_STATE_UNAVAILABLE]` note. Auto-read-off, unchanged, empty, and over-the-anchor-line-limit writes publish the same clearing transaction (a snapshot only when one was rendered, never new served rows); only a failed publication leaves the previous version's rows as the stale barrier. A second Pi session in the same workspace comes under the same discipline. The ownership, retention, and concurrency rules for anchored editing in child sessions are recorded in ADR-0007, and the integrated operation boundary in ADR-0014. The store schema is undo-free and owner-aware (version 8, #264): one layout with a required owner identity, one ref-counted connection per store path, per-store snapshot caches scoped by owner and path, and row-level version-bound conflict-free served hashes (each publication merges rows for exactly one content version and drops other versions' rows for the path in the same transaction), so the former ownerless current-version shape is unrepresentable, and a database claiming the current version must also carry the current layout — strict shape validation (exact table set, and per-table columns via `PRAGMA table_xinfo` — exact name/order/type/nullability/primary key, no defaults, no hidden or generated columns, and no extra schema objects such as views, triggers, or non-automatic indexes beyond one autoindex per expected primary key) treats a version-8 file with any deviating schema as an incompatible layout that is quarantined whole, never probed statement-by-statement; the first open of an older store — any stored schema version that is not current, any database still carrying the removed `undo` table, or the former ownerless current-version layout — quarantines that database and its sidecars once and rebuilds a fresh store, so cached snapshots and served state are lost explicitly and recover through a new read; a fresh store produces no migration residue. Corruption quarantine remains functional the same way. An unrecoverable store error fails the anchored operation. There is no user-global store: the dormant vendor user-global store and its config directory were removed with the vendored registration module, so every anchored store lives in a session directory or the temp fallback.

## Versioning

This project publishes the public npm package `@odradekk/pi-square` with Changesets. The CLI is installed as a development dependency and configured in `.changeset/config.json`. The release workflow creates a Version Packages pull request from pending changesets, then publishes the merged version through the protected `npm` GitHub Environment with npm trusted publishing. CI creates provenance, the package tag, and the GitHub release; repository secrets must never contain a long-lived npm publishing token.

Add a changeset for every change that requires a package release and select the version level for the entire `@odradekk/pi-square` package. Use `npm run changeset` to create one, `npm run changeset:status` to inspect pending releases, and `npm run changeset:version` to consume pending changesets and update package metadata and `CHANGELOG.md`. Use `npm run package:check` before release to verify the allowlisted tarball. Change detection compares against `main` and therefore requires the repository to have an initial commit.

- **patch:** Backward-compatible fixes and corrections, including metadata and documentation fixes.
- **minor:** New backward-compatible capabilities, such as tools, themes, configuration options, or other non-breaking additions.
- **major:** Breaking changes to schemas, configuration formats, tool contracts, public behavior, or supported Pi/runtime compatibility.

Tests, internal refactors, and repository maintenance that do not change shipped behavior or published documentation do not require a release. When uncertain, choose the smallest level that accurately communicates the compatibility impact and explain the decision in the changeset.

## Package Maintenance and Release Runbook

### Routine Maintenance

1. Start from an up-to-date `main` with a clean package worktree, then run `npm ci`. Do not mix release work with unrelated parent-repository or local configuration changes.
2. Make the smallest coherent implementation change. Keep the Node.js, Pi, ESM, package resource, platform, security, and ownership contracts above unless the change explicitly updates and documents them.
3. Update owned tests and documentation in the same change. Synchronize `README.md` for user-visible behavior, `AGENTS.md` for durable maintainer policy, and `THIRD_PARTY_NOTICES.md` for dependency, native binary, WASM, provenance, or licensing changes.
4. Keep `package-lock.json` synchronized with every dependency or package metadata change. Update the three `@earendil-works/pi-*` development and peer versions together when changing the supported Pi version, and update the runtime contract in both `README.md` and this file.
5. Add one changeset for every release-relevant change. Use `patch`, `minor`, or `major` according to the policy above; do not edit `package.json.version` or `CHANGELOG.md` manually.
6. Run the applicable local gates before opening a pull request:

   ```bash
   npm test
   npm run typecheck
   npm run smoke
   npm run package:check
   npm run changeset:status
   ```

7. Review `npm run package:check` for the package name, allowlisted files, executable assets, compressed and unpacked size limits, and absence of tests, credentials, local configuration, `.changeset`, or other development-only files.
8. Commit focused Conventional Commits, push a topic branch, open a ready pull request against `main`, and merge only after the `CI` workflow passes. Never bypass repository hooks or required checks for a release.

Documentation-only repository policy changes that are not included in the npm tarball do not need a changeset. User-visible README changes, package metadata changes, compatibility changes, and shipped asset changes do.

### Standard Release

1. Merge release-relevant pull requests with their changesets into `main`. The `Release` workflow must create or update the `chore: version package` pull request; maintainers do not run a separate local version commit.
2. Review the Version Packages pull request before merging. Confirm all of the following:
   - `package.json` and both root version fields in `package-lock.json` contain the same intended version.
   - `CHANGELOG.md` accurately groups every pending major, minor, and patch change.
   - Expected changeset files are consumed and unrelated files are absent.
   - The calculated version follows SemVer and no version with that number already exists on npm.
3. Merge the Version Packages pull request only when the release contents are final. A push to `main` with no remaining changesets causes `scripts/check-release.mjs` to check whether that exact version is unpublished.
4. When the publish job waits on the protected `npm` GitHub Environment, review the version, commit, workflow run, and npm registry state, then approve the deployment. Approval authorizes an irreversible registry write.
5. The publish job must use the pinned Node.js and npm versions, run `npm ci`, all tests, type checking, smoke coverage, and `npm run package:check`, then invoke `npm run release`. Publishing must use npm trusted publishing through OIDC; do not add `NPM_TOKEN`, `NODE_AUTH_TOKEN`, or another long-lived write credential to repository or environment secrets.
6. Changesets must publish the package, move `latest`, create the `v<version>` Git tag, and create the matching GitHub Release. A successful compile or npm upload alone is not a completed release.

### Failure Recovery and Security

- Before npm accepts a version, fix the cause in a normal pull request and rerun the protected workflow. The registry preflight makes retries safe by skipping versions that already exist.
