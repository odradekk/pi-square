# pi-square Agent Guide

## Project Overview

- **Name:** `pi-square` (pi-squared).
- **Language:** TypeScript using ECMAScript modules. Tests and supporting scripts also use JavaScript ESM.
- **Purpose:** A unified local extension package for the Pi coding agent. It provides prompt management, interactive and session tools, local text, file, structural, and semantic code search, persistent SSH shells, web, GitHub, and documentation tools, subagents, TUI customizations, PowerShell execution, and themes.
- **Built on:** Node.js 24, Pi 0.80.6, the Pi extension API, Pi TUI and AI packages, and TypeBox. The public npm package is loaded by Pi directly from `src/index.ts`.

## Architecture

- `src/index.ts` is the single extension entry point. It loads configuration on session start and registers each feature module.
- `src/core/` owns shared configuration, diagnostics, path handling, the session-scoped FIFO confirmation coordinator, workspace-bounded PDF input validation, and the cancellable bounded process runner used by local native tools. Strict configuration V2 merges agent-level `config/pi-square.json` with project-level `.pi/config/pi-square.json`; V1 and the former SSH `confirmCommands` field are rejected with migration diagnostics. SSH profiles and anchored editing are security-sensitive agent-only settings and are rejected in the project layer rather than merged.
- Feature directories under `src/` own individual tools or UI behavior: `anchored-edit/`, `ask-user/`, `banner/`, `codegraph/`, `display/`, `footer/`, `github/`, `notifications/`, `pdf-search/`, `prompt-manager/`, `search/`, `shell/`, `ssh/`, `subagents/`, `todo/`, and `web/`. `src/anchored-edit/` owns the vendored hash-anchor implementation, its prompt resources, the project-scoped anchored-read transform, and renderer-free workspace replace and revert definitions. `src/display/builtins.ts` owns conditional anchored-read registration and parent active-tool selection; `src/anchored-edit/workspace-replace.ts` and `src/anchored-edit/workspace-revert.ts` register the parent-only replace and revert tools through the display adapter; `src/anchored-edit/auto-read.ts` clears owner-scoped history after a successful built-in write result. The vendored edit registration remains unimported. `src/display/` owns the shared declarative description contract, catalog and policy resolver, sanitization/redaction, semantic theme mapping, responsive layout/components, diff and projected write preview, one session motion scheduler, runtime lifecycle, `/display` manager, Pi built-in overrides and conflict diagnostics, internal tool adapters, and the public Adapter v1 lifecycle. `src/footer/` owns the stateless native-data snapshot and operational footer lifecycle. `src/github/` owns the authenticated GitHub REST client and bounded read-only tools shared by the parent session and explicitly opted-in child profiles. `src/pdf-search/` owns local PDF.js text extraction, normalized exact and conservative fuzzy page matching, and bounded in-memory caching. `src/web/` owns Jina and Context7 integrations plus the parent-only Firecrawl PDF parser, including workspace-bounded page extraction, confirmed upload, and bounded HTTP handling. `src/shell/` owns platform shell selection, PowerShell process execution, and bounded streaming output; `src/display/` owns parent shell presentation and non-Windows built-in bash registration. `src/subagents/` owns V2 definition overlays, layered prompt compilation and audit manifests, parent-session-owned persisted child execution, portable child tool policy, background delivery, bounded live updates, the `delegate`/`resume` tools, the integrated `/subagent` manager, the configuration-guide custom message, and the bounded background status.
- `src/search/` owns the bounded `rg` and `fd` wrappers, argument construction, native-binary resolution, and structured output. `rg` and `fd` use Git-tracked binaries without PATH fallback. `rg` exposes 8 fields (`pattern`, `path`, `globs`, `literal`, `context`, `filesOnly`, `offset`, `limit`; max limit 25) with a `filesOnly` mode that returns file paths with match counts. `fd` exposes 8 fields (`pattern`, `path`, `excludeGlobs`, `types`, `extensions`, `maxDepth`, `offset`, `limit`; max limit 100) using `StringEnum` for `types` items.
- `src/codegraph/` owns the local semantic `codegraph` tool, exact platform-bundle resolution, workspace path boundary, index-health and lifecycle policy, and bounded execution. The parent definition exposes `explore`, `status`, confirmed `init`, automatic incremental `sync`, and confirmed `reindex`; child definitions are restricted to `explore` and `status`.
- `src/ssh/` owns the parent-only persistent SSH tool, exact `ssh2` client integration, pinned host verification, agent/private-key authentication, masked secret input, guarded connection-event lifecycle, bounded raw output cursors, single-line terminal projection, connection/session limits, idle cleanup, and lifecycle teardown. It supports one POSIX foreground command per shell and no child exposure, arbitrary targets, password parameters, agent forwarding, output artifacts, transparent reconnect, SFTP, jump hosts, proxies, or port forwarding.
- `src/tool-catalog.ts` defines the extension tools that may be exposed to subagents.
- `subagents/` contains the required `promptVersion: 2` YAML definitions for bundled subagent roles. Effective definitions overlay package, agent, and nearest-project fields in that precedence order.
- `themes/` contains the matched light and dark Pi themes.
- `bin/` vendors cross-platform `rg` and `fd` executables.
- `tests/` contains contract, unit, integration, and smoke coverage. `tests/run.mjs` is the main test-suite orchestrator, while `tests/smoke.mjs` exercises a real Pi session.

Keep functionality within its owning module. Shared code belongs in `src/core/` only when it is genuinely used across features.

## Rules and Constraints

- Preserve the Node.js 24 and Pi 0.80.6 runtime contract unless the change explicitly updates compatibility and documentation.
- Keep the project ESM-only and compatible with the strict settings in `tsconfig.json`, including unused-symbol checks and no emitted JavaScript.
- Register extension behavior through `src/index.ts`. The package exports only `.`, the intentional declarative `./display` integration API, and `./package.json`; do not add other package entry points or deep-import contracts without an explicit architecture change.
- Validate external configuration and tool inputs at their boundaries. Reject unknown or invalid configuration rather than relying on unchecked values internally.
- Keep every model-callable tool parameter schema provider-compatible: use a strict top-level `Type.Object` with `additionalProperties: false`; never use top-level `Type.Union`, `anyOf`, or `oneOf`. Represent operation or mode branches with a required `StringEnum`, enforce branch-specific field combinations at execution validation, and add contract coverage for the top-level object shape, absent unions, and required discriminator. Split a branch into its own tool when a branch-specific field must not appear in sibling branches at all: models served through the OpenAI Responses API populate every declared schema property, so a field that sibling modes reject (such as the resume-only `id`) would make the shared schema unusable for them. This is why subagents expose `delegate` (fg/bg) and `resume` (id/task) as separate tools; their execution validation also treats blank optional strings as unset.
- Keep non-secret settings in agent-level `config/pi-square.json` or project-level `.pi/config/pi-square.json`. SSH profiles and both `anchoredEditing` settings (`enabled` and `autoRead`) are agent-only; project layers that contain `ssh` or `anchoredEditing` are rejected atomically. Display policy precedence is fixed as package defaults, agent defaults/family/tool, then project defaults/family/tool, so project scope wins over all agent specificity. `/display` writes must retain canonical-scope, lock/CAS, symlink/identity, complete-candidate validation, mode-preservation, atomic-rename, stale-review, and project-trust guarantees. `footer.mode` remains only a deprecated accepted layer input with no runtime effect until reviewed removal. Credentials and model definitions belong to Pi-owned `auth.json` and `models.json`; never commit secrets.
- Keep GitHub tools read-only and GitHub.com-only. Resolve `GITHUB_TOKEN` before `auth.json` `github.key`; never expose either value in content, details, errors, logs, or rendering. Authenticated redirects must remain on `https://api.github.com`, all remote and model-facing data must have explicit budgets, and every remote/local truncation must remain visible. The tools are opt-in child capabilities for trusted local definitions; among bundled roles only Librarian receives them, with no built-in, general web, Context7, shell, or write tools. Generalist and the other bundled specialists must not receive PAT capabilities. Private repository results persist in normal parent or child session history and resumable child artifacts, while the GitHub module itself creates no additional cache, log, or artifact.
- Keep Firecrawl PDF parsing parent-only and explicit about local data upload. Resolve `FIRECRAWL_API_KEY` before `auth.json` `firecrawl.key`; never expose the key in content, details, errors, logs, or rendering. Canonicalize PDF paths below cwd through symlinks, require a user confirmation for every upload to the fixed `https://api.firecrawl.dev/v2/parse` endpoint, reject encrypted or oversized PDFs before confirmation, and send only an in-memory PDF containing the sorted unique requested pages. Preserve the 50-page, 50-MB, remote-response, timeout, and model-output bounds; make truncation visible; do not retry sent requests; keep ZDR behavior and its data-handling consequence explicit. Do not expose `parse` through the child tool catalog while confirmation is unavailable in child sessions.
- Keep `pdf_search` local, read-only, and workspace-bounded. Use only package-local PDF.js CMap, font, and WASM assets with no remote document or runtime asset fetches. Preserve the 50-MB, 1,000-page, per-page/document text, 30-second, result, and 64/128-MiB cache bounds; reject encrypted and textless PDFs explicitly; return no partial result after timeout or resource failure. Keep the cache memory-only, clear the parent cache on session start, key entries by canonical file identity, and invalidate changed files before reuse. Preserve exact-first conservative matching, language-neutral normalization, best-effort context ordering, and the no-OCR/no-semantic-search scope. The parent registers the tool; the child catalog permits explicit trusted opt-in, while bundled roles omit it.
- Keep the bundled role catalog to five visible complementary profiles: Explorer for local evidence, Oracle for complex reasoning with observational execution and external lookup, Crawler for focused web and Context7 research, Librarian for authenticated GitHub research, and Generalist for scoped writable work. Oracle's tool envelope contains Crawler's, so those two stay complementary by purpose and cost rather than by capability, and Oracle's non-mutating boundary is enforced by its policy text rather than by its tools; see ADR-0006. Package profiles omit model and effort so fresh runs inherit the parent values; same-ID resume keeps the original frozen values. All profiles inherit the parent system. Every bundled specialist disables discovered skills, while Generalist receives the explicit non-GitHub tool set and all discovered skills.
- Preserve explicit tool-list semantics: omitted or empty `tools` selects runtime defaults, the exclusive `tools: [none]` sentinel selects no built-in tools, and extension tools remain opt-in. Persist the logical selection so resume re-resolves platform capabilities without silently broadening access.
- Preserve feature ownership and avoid unrelated refactors. Add shared abstractions only when multiple modules have a demonstrated common requirement.
- Keep model-callable shell tools platform-exclusive: non-Windows sessions expose bash only, Windows sessions expose pwsh only, and subagents request the portable `shell` capability rather than declaring both names. Parent non-Windows bash is registered only by `src/display/builtins.ts`; `src/shell/` registers only Windows pwsh and platform call guards.
- Keep the fixed visual grammar in code, not in configuration. The shipped grammar renders one static `●` for every tool entry in every state, color carries the state through existing semantic tokens, and a distinguishable fallback glyph set replaces color when the runtime reports no color. The `family` field stays in the catalog and keeps selecting the owning adapter; it does not select a glyph. The title carries the tool identity; no family icon is rendered. Titles are sentence case and unique within each family (`Grep` versus `Text search`). The header is always exactly one row: a long target is truncated with `…` and never wraps, a path target follows C2 (workspace-relative, `~` under the home directory, middle elision that never loses the file name), and a bounded, truncated, or partial result carries the matching header badge instead of a body notice. Each fallback marker measures one cell, and a bounded header badge renders for each qualifier except `warning`. The marker never animates; the scheduler drives only the elapsed duration at 120 ms for `full`, 1 s for `reduced`, and not at all for `off`. Compact layouts drop the duration first and keep only the highest-priority badge. The collapsed body is one summary row that states the outcome in counts and sizes; only the payload tools (`edit`, `replace`, `revert`, `write`, `bash`, `pwsh`, `ssh`, `grep`, `rg`, `pdf_search`, `codegraph`, `search`, `fetch`, `libs`, `docs`, `parse`, `github`, `delegate`, `resume`) keep a bounded body above that row. A failure states one human sentence, and the raw platform text appears exactly once, in an expanded `ERROR` section. Expanded sections that only restate the header (`FILE`, `TARGET`, `DIRECTORY`, `QUERY`, `REQUEST`, `SUMMARY`, `ACTION`, `PERSISTENCE`, `STATUS`) are pruned before render, and a label-led section rule renders only between two or more sections. A body never ends with an empty row, and a truncation notice is never a numbered content line. Visual acceptance must assert the bullet marker, the fallback glyph set, badge presence, marker widths, the one-row header, and the absence of family icons through the production decoration path rather than through synthetic descriptions alone.
- Keep the shared operational display declarative and theme-portable. All parent tools and pi-square-owned TUI surfaces use `src/display/` sanitization, budgets, standard semantic theme tokens, responsive boundaries, and the one session-owned scheduler at 120 ms intervals (`full`), 1 s intervals (`reduced`), or static (`off`). Runtime-independent tool definitions remain renderer-free; parent registrars apply the owning declarative adapter, production tests exercise those decorated definitions, and a result must visually replace the pending call rather than render as a second operational entry. Expanded results use the closed internal `DisplaySection` model from `src/display/types.ts`; public Adapter v1 remains limited to its published field kinds and does not accept internal sections. Background subagent completion messages are the explicit native-shell exception. Tests, CI, non-TTY, and incapable environments downgrade deterministically. Do not patch ordinary user/assistant message components, introduce a second required palette, retain native/legacy renderer branches, or let child tool construction require a parent display runtime.
- Keep Pi built-in overrides factory-faithful and ownership-aware. Recreate `read`, `grep`, `find`, `ls`, `edit`, `write`, and non-Windows `bash` only from Pi 0.80.6 public factories, spread the original definition, and replace renderer fields only. The sole declared exception is `read`'s conditional anchored-read guard and post-factory model-visible content transform; no other execution or model-content wrapper is allowed. When `anchoredEditing.enabled` is false, read prompt metadata, execution results, errors, and active-tool selection remain factory-faithful, including Pi `edit` at its factory position. When enabled, only workspace text is anchored; the parent-only renderer-free `replace` and `revert` tools use the same project store and replace Pi `edit` in the active parent list. `replace` persists one owner-scoped revert record before modification and rolls it back if its write fails. `revert` restores only that latest record, refuses modified or deleted files as a completed warning, and returns its authoritative anchored diff. A successful Pi `write` result clears that file's revert and served state; a failed result leaves both intact. `anchoredEditing.autoRead` is agent-only, defaults to true, appends bounded fresh anchors after changed successful writes, and controls the post-edit anchored results for replace and revert without changing cleanup. Supported images keep Pi attachments, named guard responses cover outside paths and non-text inputs, and project `.pi/anchored-edit/hash-store.sqlite` state uses the `parent` owner. The vendored edit registration stays unimported. Preserve `images.autoResize`, `shellPath`, and `shellCommandPrefix` through one public `SettingsManager`; parsing failures block only read/bash and retain native or last-valid behavior. Never wrap Pi edit/write execution or their mutation queue. Projected write previews are workspace-bounded, regular UTF-8 text files only, capped at 1 MB, TOCTOU checked, and explicitly non-authoritative. Block all overrides for the known pi-tool-display global marker; detect earlier winning owners through public `sourceInfo`, surface bounded persistent diagnostics, and document the unobservable later-losing-owner blind spot. Do not monkey-patch `registerTool` or use private Pi APIs.
- Keep anchor-store state owner-scoped and workspace-bounded. Enabled parent operations use the `parent` owner at `.pi/anchored-edit/hash-store.sqlite` only after canonical workspace path validation, including symlinks. When `anchoredEditing.enabled` is on, a writable subagent's read is the anchored read: it is composed from Pi's public `createReadToolDefinition` plus the shared anchor transform and guard (via `src/anchored-edit/child-read.ts` and the shared `read-tool.ts` wrapper), carries no pi-square display shell, and overrides the child's built-in read so exactly one read tool is offered. Its served rows are recorded under the child's own owner (its subagent ID), so the parent's served record and each child's record never mix; read-only roles and disabled anchored editing receive no anchored tools. Store corruption is quarantined and rebuilt on open. An unrecoverable store error fails the anchored operation, and a failed undo-record persistence refuses the replace before it writes. Do not migrate the dormant vendor user-global store into the project store.
- Keep pi-square components that Pi renders in each frame caching their rendered lines by width and content, like the Pi built-in components. `OperationalDisplayComponent` returns its cached lines while the description, policy, theme, render options, and width stay the same; `update()` and `invalidate()` drop the cache so a running tool still refreshes its duration at the motion interval, a result replaces the pending call, and an expand, collapse, theme change, or terminal-width change produces newly calculated lines.
- Keep `@odradekk/pi-square/display` Adapter v1 static and bounded. It may map at most 16 fields using only `text`, `path`, `url`, `count`, `command`, `preview`, `diff`, and `progress`; paths, labels, and titles retain their published bounds. Reject functions, accessors, Components, raw renderers, arbitrary theme tokens, and unknown fields. The absent-runtime queue remains versioned and capped at 128; activation mutates the explicitly declared tool object by retained identity; disposal restores original property descriptors only while pi-square still owns them and requeues declarations for runtime replacement. Never scan or intercept third-party/MCP tools automatically.
- Keep SSH parent-only and agent-configured. Project configuration must not define or override SSH profiles; model calls may select only a configured profile and allowlisted target. Always verify one of the target's pinned OpenSSH SHA-256 fingerprints, disable agent forwarding, permit only SSH-agent or referenced private-key authentication, and keep passphrases and runtime secrets out of model parameters, content, details, rendering, logs, and artifacts. Alternate targets require once-per-parent-session endpoint confirmation, connected sessions run commands without per-command confirmation, and masked input requires the interactive TUI. Preserve the global/profile limits, idle cleanup, one-active-command invariant, explicit disconnect state, current-parent-session lifetime, 256-KiB raw in-memory output ring, visible cursor expiry, and no local output spill. Keep an `error` listener on every `ssh2` client from creation through close, clean phase listeners before ownership transfer, and release the transport idempotently when its shell channel disconnects; never mask lifecycle defects with a process-level exception handler. Preserve raw cursor accounting while projecting carriage-return, backspace, and erase-line refreshes into latest-visible model and TUI output, without expanding into full-screen terminal emulation. Do not expose SSH through `src/tool-catalog.ts` or bundled child roles, and do not add password login, arbitrary targets, full-screen terminal emulation, automatic reconnect, cross-session daemons, SFTP, jump hosts, proxies, forwarding, or a system-SSH fallback without an explicit redesign.
- Keep all pi-square `ctx.ui.confirm` calls behind the one session-scoped FIFO coordinator because the pinned Pi TUI exposes one extension selector at a time. Reset the coordinator on parent session start and shutdown, preserve each tool's declined/aborted semantics, and serialize only confirmation prompts rather than the approved operations.
- Keep CodeGraph local, workspace-bounded, and explicit about persistent writes. Resolve the exact `@colbymchenry/codegraph` platform package directly without PATH or npm-shim fallback; force telemetry, update checks, downloads, and watchers off. `init` and `reindex` require Pi confirmation, incremental `sync` may run automatically, and no definition may expose upstream install/uninstall/uninit/unlock/upgrade/daemon operations. Parent calls may use the complete operation set, while Explorer, Oracle, and Generalist must receive the read-only `explore`/`status` schema. Crawler and Librarian must not receive CodeGraph.
- Keep subagent prompt authority explicit: immutable governance, optional inherited parent core, V2 `policy`, and call policy form SYSTEM; replayed `instructions`, reference-only parent history, current task, and replayed `output` form the delegated user message. Do not let parent history authorize work or silently apply changed definitions to an existing child ID.
- Keep V2 definition overlays source-aware and atomic. Package definitions are read-only; agent and project writes must stay directly inside their validated scope directory. Omitted fields inherit, explicit null/empty values clear, and effective fields retain source path/hash provenance.
- Keep footer behavior native-semantic and stateless: derive cumulative usage, session identity, model/provider, subscription cost, and context directly from Pi's read-only context on each render; consume branch and extension statuses from `ReadonlyFooterDataProvider`; never add independent git polling or persisted usage counters. The footer memoizes the derived usage totals and session name by session entry count, recomputing only after an entry is appended; the memo holds in-memory derived values for the current entry set, never a persisted counter. The operational footer always installs in TUI mode, uses two responsive rows plus a conditional status row, has no native/legacy branch, and must remain bounded at all 39/40/63/64/80/99/100/120-column boundaries in bundled and third-party themes.
- Keep subagent presentation and manager metadata privacy-preserving: render from bounded v3 details without exposing prompt snapshots, custom system text, raw session data, or normal-run artifact paths. Primary tool output, Config Guide, and manager use the shared unframed operational interface grammar with a one-cell status rail, restrained semantic color, label-led section rules, and width-aware activity/footer alignment. Background completion custom messages are the deliberate exception: deliver `done` and `error` results as steering messages with turn triggering so active parents receive them at the next model boundary and idle parents start a new turn, then render the shared canonical run description inside Pi's native success/error tool shell. The transcript entry and the completion message must keep using one description builder rather than a parallel component tree. ACTIVITY, manager, and the subagent status row must consume one shared allowlisted tool-call formatter, including specialized `github` summaries; unknown tools show only `called`, and no surface may render tool result payloads or arbitrary argument objects. Subagents publish footer state only through `ctx.ui.setStatus`; the footer consumes that bounded text without inspecting child results. Do not introduce emoji presentation characters, decorative background cards, or undifferentiated log rows.
- Keep `/subagent` lifecycle management scoped to the current parent session and inside one non-overlay, focus-preserving manager workflow. Foreground cancellation stays with Pi's native turn cancellation; queued/background manager cancellation must pass through `cancelling` before terminal `aborted`, retain resumable artifacts, and require separate confirmation for history deletion. Resume eligibility is determined by the activity lease, not the persisted phase: inactive stale `running` records remain recoverable, while an active lease must disable Manager resume and make every direct or raced resume fail with the retryable `SUBAGENT_ACTIVE` tool error before session history is changed. Parameterized `/subagent <request>` calls must append the bounded custom Config Guide before sending the unchanged native user request, with both ordered as follow-ups and only the user message triggering a turn.
- Add or update focused tests for behavior changes. Defect fixes require a regression test, and public contract changes require contract coverage.
- Treat `bin/` as security-sensitive vendored assets. Do not modify or replace them without verifying provenance, supported targets, runtime constraints, and applicable notices.
- Treat `@colbymchenry/codegraph`, its six optional platform packages, bundled Node runtime, and parser WASM assets as security-sensitive runtime dependencies. Keep every package on one exact version, verify all six lockfile integrities and supported targets on upgrades, and preserve direct platform-package resolution with no network self-heal.
- Treat `pdfjs-dist`, its CMap/font/WASM assets, and transitive optional `@napi-rs/canvas` native packages as security-sensitive runtime dependencies. Keep `pdfjs-dist` exact, verify its integrity and Node compatibility, verify the lockfile integrities and target metadata of the canvas packages on upgrades, resolve assets directly from the installed package, and never add a network fallback. PDF text extraction must not invoke rendering APIs or external processes.
- Treat `ssh2`, its key parsing dependencies, and optional `cpu-features` native addon as security-sensitive remote-execution dependencies. Keep `ssh2` exact, verify lockfile integrity and Node 24 behavior on upgrades, preserve the explicit CommonJS bridge, never omit `hostVerifier`, and retain the pure-JavaScript fallback when the optional native addon is unavailable.
- Keep `THIRD_PARTY_NOTICES.md` synchronized with every vendored binary, native runtime dependency, or licensing change.
- Prefer existing dependencies and platform APIs. Inspect `package.json` and `package-lock.json` before adding a dependency, and keep the lockfile synchronized.
- Preserve unrelated working-tree changes. Keep each change focused and review the final diff before completion.

## Quality Gates

Apply the current gates according to the change risk:

- For code changes, run `npm test` and `npm run typecheck`.
- Also run `npm run smoke` when a change affects extension loading, module or tool registration, prompt composition, skill discovery, configuration integration, or other end-to-end Pi behavior.
- Changes to shell platform selection, PowerShell encoding, process-tree cancellation, or streaming require real Windows validation with PowerShell 7 and Windows PowerShell 5.1 before commit, in addition to injected-platform and Linux process tests.
- For documentation-only changes, verify referenced paths, versions, commands, and links against the repository. Code checks are not required unless the documentation change accompanies code.
- For changes to the operational display component, the footer snapshot, or any pi-square surface that Pi renders in each frame, run `npm run bench:frames` to confirm the change does not regress frame cost. The report is a development tool, not a required CI gate; wall-clock timings are not deterministic and must not be asserted in CI.
- Report every check run and any check that could not run. A passing type check does not replace behavioral testing.

GitHub Actions runs tests, type checking, smoke coverage, and publication tarball validation for pull requests and `main`. There is currently no configured linter. The planned lint gate is ESLint flat config with typescript-eslint, covering `src/**/*.ts` and applying appropriate JavaScript rules to `tests/**/*.mjs`. Do not require `npm run lint` until the dependencies, configuration, script, and an initial passing baseline are committed.

## Versioning

This project publishes the public npm package `@odradekk/pi-square` with Changesets. The CLI is installed as a development dependency and configured in `.changeset/config.json`. The release workflow creates a Version Packages pull request from pending changesets, then publishes the merged version through the protected `npm` GitHub Environment with npm trusted publishing. CI creates provenance, the package tag, and the GitHub release; repository secrets must never contain a long-lived npm publishing token.

Add a changeset for every change that requires a package release and select the version level for the entire `@odradekk/pi-square` package. Use `npm run changeset` to create one, `npm run changeset:status` to inspect pending releases, and `npm run changeset:version` to consume pending changesets and update package metadata and `CHANGELOG.md`. Use `npm run package:check` before release to verify the allowlisted tarball. Change detection compares against `main` and therefore requires the repository to have an initial commit.

- **patch:** Backward-compatible fixes and corrections, including metadata and documentation fixes.
- **minor:** New backward-compatible capabilities, such as tools, themes, configuration options, or other non-breaking additions.
- **major:** Breaking changes to schemas, configuration formats, tool contracts, public behavior, or supported Pi/runtime compatibility.

Tests, internal refactors, and repository maintenance that do not change shipped behavior or published documentation do not require a release. When uncertain, choose the smallest level that accurately communicates the compatibility impact and explain the decision in the changeset.

## Package Maintenance and Release Runbook

### Routine Maintenance

1. Start from an up-to-date `main` with a clean package worktree, then run `npm ci`. Do not mix release work with unrelated parent-repository or local configuration changes.
2. Make the smallest coherent implementation change. Keep the Node.js, Pi, ESM, package resource, platform, security, and ownership contracts above unless the change explicitly updates and documents them.
3. Update owned tests and documentation in the same change. Synchronize `README.md` for user-visible behavior, `AGENTS.md` for durable maintainer policy, and `THIRD_PARTY_NOTICES.md` for dependency, native binary, WASM, provenance, or licensing changes.
4. Keep `package-lock.json` synchronized with every dependency or package metadata change. Update the three `@earendil-works/pi-*` development and peer versions together when changing the supported Pi version, and update the runtime contract in both `README.md` and this file.
5. Add one changeset for every release-relevant change. Use `patch`, `minor`, or `major` according to the policy above; do not edit `package.json.version` or `CHANGELOG.md` manually.
6. Run the applicable local gates before opening a pull request:

   ```bash
   npm test
   npm run typecheck
   npm run smoke
   npm run package:check
   npm run changeset:status
   ```

7. Review `npm run package:check` for the package name, allowlisted files, executable assets, compressed and unpacked size limits, and absence of tests, credentials, local configuration, `.changeset`, or other development-only files.
8. Commit focused Conventional Commits, push a topic branch, open a ready pull request against `main`, and merge only after the `CI` workflow passes. Never bypass repository hooks or required checks for a release.

Documentation-only repository policy changes that are not included in the npm tarball do not need a changeset. User-visible README changes, package metadata changes, compatibility changes, and shipped asset changes do.

### Standard Release

1. Merge release-relevant pull requests with their changesets into `main`. The `Release` workflow must create or update the `chore: version package` pull request; maintainers do not run a separate local version commit.
2. Review the Version Packages pull request before merging. Confirm all of the following:
   - `package.json` and both root version fields in `package-lock.json` contain the same intended version.
   - `CHANGELOG.md` accurately groups every pending major, minor, and patch change.
   - Expected changeset files are consumed and unrelated files are absent.
   - The calculated version follows SemVer and no version with that number already exists on npm.
3. Merge the Version Packages pull request only when the release contents are final. A push to `main` with no remaining changesets causes `scripts/check-release.mjs` to check whether that exact version is unpublished.
4. When the publish job waits on the protected `npm` GitHub Environment, review the version, commit, workflow run, and npm registry state, then approve the deployment. Approval authorizes an irreversible registry write.
5. The publish job must use the pinned Node.js and npm versions, run `npm ci`, all tests, type checking, smoke coverage, and `npm run package:check`, then invoke `npm run release`. Publishing must use npm trusted publishing through OIDC; do not add `NPM_TOKEN`, `NODE_AUTH_TOKEN`, or another long-lived write credential to repository or environment secrets.
6. Changesets must publish the package, move `latest`, create the `v<version>` Git tag, and create the matching GitHub Release. A successful compile or npm upload alone is not a completed release.

### Post-Release Verification

After every release, verify all public surfaces before declaring completion:

```bash
npm view @odradekk/pi-square name version dist-tags --json
npm view @odradekk/pi-square@<version> dist --json
gh release list --repo odradekk/pi-square --limit 5
RELEASE_AGENT_DIR="$(mktemp -d)"
PI_CODING_AGENT_DIR="$RELEASE_AGENT_DIR" pi install npm:@odradekk/pi-square
```

- Confirm `latest` points to the new stable version and no bootstrap, prerelease, or deprecated version owns `latest`.
- Confirm npm exposes an attestation URL and SLSA provenance for the released version, and that the provenance identifies `odradekk/pi-square`, `.github/workflows/release.yml`, `main`, and the `npm` Environment.
- Confirm the GitHub Release is non-draft, non-prerelease, and uses the expected `v<version>` tag.
- Install into an isolated `PI_CODING_AGENT_DIR`; verify the package version, allowlisted assets, TypeScript extension entry, themes, and representative tool registration without changing the maintainer's active Pi configuration.
- For a release defect, publish a new patch version through the same workflow. npm versions are immutable: never overwrite, reuse, or silently replace a published version.

### Failure Recovery and Security

- Before npm accepts a version, fix the cause in a normal pull request and rerun the protected workflow. The registry preflight makes retries safe by skipping versions that already exist.
- If trusted publishing returns `ENEEDAUTH` or `E404`, do not fall back to a write token. Verify the npm CLI version, `id-token: write`, GitHub-hosted runner, package `repository.url`, and the case-sensitive npm trusted-publisher fields: owner `odradekk`, repository `pi-square`, workflow `release.yml`, Environment `npm`, and allowed action `npm publish`.
- If npm accepted the version but tag or GitHub Release creation failed, first verify the registry version and integrity, then rerun or repair only the missing Git metadata. Do not publish the same version again.
- Keep the `npm` Environment restricted to `main` with required reviewer approval. Keep Actions pinned to reviewed commit SHAs and preserve the minimum job-level permissions.
- Keep npm package publishing set to require 2FA and disallow traditional tokens. Any temporary bootstrap credential must be short-lived, scoped to the minimum package operation, kept out of files and logs, and revoked immediately after OIDC succeeds.
- Treat unexpected tarball files, missing provenance, changed native asset hashes, registry/tag divergence, or a release from an unrecognized workflow as a release-blocking security incident.
