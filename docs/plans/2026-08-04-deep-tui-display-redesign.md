# Plan: Deep operational-console TUI redesign for every pi-square display surface

Date: 2026-08-04
Tier: Deep

## Goal

Replace pi-square's fragmented tool and extension presentation with one high-density operational-console display system. The finished major release covers every pi-square tool, every pi-square-owned TUI surface, and Pi's built-in tools; adds per-tool configuration and a `/display` manager; exposes a declarative public adapter API; and preserves model-facing behavior, privacy boundaries, bounded output, theme portability, and reload safety.

## Context

- `src/index.ts:1-61` registers the current feature modules and reloads strict configuration during `session_start`. The configuration handler is registered before feature handlers, so a display runtime created during extension setup can read the newly loaded config when its own `session_start` handler runs.
- `src/core/config.ts:11-21,121-265` defines strict agent/project V2 layers with `additionalProperties: false`, rejects an invalid layer atomically, and currently merges only `footer.mode` and `banner.enabled`. `loadConfig()` returns file-level `sources`, but there is no field-level provenance and no config writer.
- Tool presentation is split across `src/ask-user/render.ts`, `src/codegraph/render.ts`, `src/github/render.ts`, `src/pdf-search/render.ts`, `src/scheme/render.ts`, `src/search/render.ts`, `src/shell/render.ts`, `src/ssh/render.ts`, `src/subagents/render.ts`, `src/todo/render.ts`, `src/web/shared/render.ts`, and inline renderers in `src/web/tools/`. `src/time/index.ts` has no renderer; the non-Windows bash wrapper in `src/shell/index.ts:53-57` replaces only `renderCall`.
- Shared layout and sanitization are duplicated. `src/search/render.ts:24-93` owns control escaping and hanging text, `src/web/shared/render.ts:1-180` owns terminal and Markdown sanitization, and `src/subagents/render.ts:29-128` owns responsive rows and section components.
- Non-tool TUI surfaces are independently implemented in `src/footer/`, `src/banner/index.ts`, `src/subagents/manager.ts`, `src/subagents/status.ts`, `src/todo/widget.ts`, `src/ask-user/prompt.ts`, `src/ssh/secret-input.ts`, and subagent custom message renderers. All `ctx.ui.confirm` calls must remain behind `src/core/confirmation.ts`.
- `src/subagents/tool-display.ts:1-156` is the required allowlisted tool-call formatter shared by ACTIVITY, manager, and status presentation. Unknown tools expose only `called`; the unified display system must preserve that privacy rule.
- Pi 0.80.6 publicly exports all seven `create*ToolDefinition` factories, `SettingsManager`, `getAgentDir`, `renderDiff`, diff generators, syntax highlighting, truncation helpers, and the `ToolDefinition` rendering contract. Each built-in definition can therefore be copied and display-decorated without private imports or a `registerTool` monkey patch.
- Pi extension tool registration is first-wins between extensions, while an extension definition with a built-in name replaces the built-in definition. Public APIs expose only the winning owner. Conflict detection can inspect the winning `sourceInfo` and the known `Symbol.for("pi-tool-display.api.v1")` marker, but cannot discover an unknown renderer that registers after pi-square and loses.
- Registering `grep`, `find`, or `ls` as extension overrides can change the active tool set. Built-in registration must snapshot `pi.getActiveTools()` and restore the exact list after registration. Windows must continue to expose `pwsh` instead of `bash`.
- The current shell override creates bash without Pi's effective `shellPath` and `shellCommandPrefix`; independently recreating read also risks losing `images.autoResize`. Public `SettingsManager.create(ctx.cwd, getAgentDir(), { projectTrusted: ctx.isProjectTrusted() })` and its getters provide all three values when settings parse successfully. A settings parse error must block only the affected read/bash display overrides, because a newly created manager cannot reproduce Pi's retained last-valid settings state after malformed reload input.
- Valid Pi themes contain the standard semantic token set. Unknown theme tokens throw. The redesign may use only standard tokens such as `toolTitle`, `toolOutput`, `accent`, `muted`, `success`, `warning`, `error`, `borderMuted`, and the standard diff/background tokens; bundled themes may change values but may not define required private tokens.
- Existing rendering tests use real and plain themes and enforce bounded 40/80/120-column output. `tests/contract.test.mjs` protects schemas, tool catalogs, commands, renderers, and active tools; `tests/smoke.mjs` loads a real Pi session. CI is Linux-only, while `AGENTS.md` requires real PowerShell 7 and Windows PowerShell 5.1 validation for shell streaming changes.
- `package.json` currently has no `exports`. Adding `.` and `./display` is a deliberate major-version encapsulation change. `scripts/verify-pack.mjs` already permits `src/`, but the public display entry must be added to its required-file list and covered by `tests/release/package.test.mjs`.

## Approach

Create a session-owned `DisplayRuntime` under `src/display/` and inject it into parent feature registrars from `src/index.ts` as each tool family migrates. Tool-definition factories used by `src/tool-catalog.ts` retain zero-required-argument construction and execution contracts; parent registrars decorate their returned definitions, while headless child definitions remain constructible without a parent runtime and parent-visible child activity continues through the shared declarative summary formatter. Internal adapters convert trusted tool args/details into a closed `DisplayDescriptionV1`; shared components alone construct TUI output, sanitize untrusted text, apply budgets, resolve per-tool policy, animate pending states, and render responsive layouts. Migrated parent tools use `renderShell: "self"` and preserve their schemas, prompt metadata, execution mode, execution implementation, model-facing result content, and security checks.

The visual grammar is fixed: a one-cell status rail (`Braille spinner` while pending, `✓` success, `!` warning, `×` error, `–` aborted), a compact title and primary target on the first row, right-priority timing/state metadata, two-space-indented secondary rows, and strong framing only for diffs, confirmations, editors, and managers. Layout tiers remain compact below 64 columns, regular from 64 through 99, and wide from 100 columns. Motion is globally `full | reduced | off`; full uses one shared scheduler capped at 5 frames per second, reduced updates once per second, and off creates no timer. Frames have equal visual width, and non-TUI, non-TTY, `TERM=dumb`, and test environments automatically reduce or disable motion.

Display configuration remains V2 and uses `display.defaults`, fixed `display.families`, and dynamic `display.tools` overlays. The closed policy fields are `resultMode` (`hidden | summary | preview`), `previewLines` (1-80), `expandedMaxLines` (0-20000), `showMetadata`, `showDuration`, `wordWrap`, `diffView` (`auto | split | unified`), `diffSplitMinWidth` (70-240), `diffCollapsedLines` (4-240), and `diffIndicators` (`bars | classic | none`). Errors, confirmations, secret-input prompts, and security warnings ignore `hidden`. Global defaults are summary output, 8 preview lines, 4000 expanded lines, metadata and duration enabled, wrapping enabled, auto diff at 120 columns, 24 collapsed diff lines, and bar indicators. Families are `filesystem`, `search`, `execution`, `remote`, `workflow`, and `agent`; every built-in and pi-square tool has exactly one catalog entry. `display.tools` accepts at most 128 names matching `^[A-Za-z0-9][A-Za-z0-9_.:-]{0,63}$`, and every nested overlay remains a strict object. Effective policy applies overlays in this exact order: package defaults, agent defaults, agent family, agent tool, project defaults, project family, project tool. Project scope therefore wins over every agent-scope specificity, matching the existing config layer precedence. Successful display saves replace the in-memory config/provenance and invalidate active display components immediately; only external ownership conflict resolution requires `/reload`. The manager defaults to the agent scope; project writes require an explicit scope change and a review screen.

The rejected approaches are a pi-tool-display dependency or vendored fork, arbitrary TUI callbacks in the public API, global `registerTool` interception, private Pi runner inspection, and a native/legacy renderer fallback. Existing `footer.mode` remains accepted only as a deprecated V2 input that emits a warning and has no effect, so old config files are not discarded atomically while the native footer fallback is removed.

## Risks & open questions

- Public Pi APIs cannot discover an unknown renderer that registers after pi-square and loses first-wins ownership. The accepted boundary is best-effort detection through the winning `sourceInfo` plus the known pi-tool-display global marker; documentation and diagnostics must not claim complete conflict discovery.
- Adding `package.json` exports intentionally blocks undeclared deep imports. This is covered by the major release and must be called out in migration notes even though no in-repository consumer uses a bare package deep import.
- Rich motion can regress CPU usage or cause terminal flicker. The one-scheduler design, 5 FPS cap, deterministic downgrade, fixed-width frames, disposal tests, and real tmux/SSH/Windows exercises are release blockers rather than optional polish.
- Pending write diff previews introduce display-only file reads and can race with queued mutations. They are explicitly labeled projected, never replace write execution, never appear as authoritative final diffs, and remain bounded by workspace canonicalization, symlink revalidation, regular-file checks, the 1 MB ceiling, and summary fallback.
- The `/display` manager is the first writer for `config/pi-square.json` and `.pi/config/pi-square.json`. Root canonicalization, symlink rejection, token-owned stale locks, compare-and-swap review fingerprints, candidate-wide strict validation, unrelated-key preservation, trusted project scope, mode preservation, atomic rename, and Linux/Windows failure tests are required before any renderer consumes saved overrides.
- Recreated read/bash factories cannot safely match Pi when effective settings fail to parse. The accepted failure behavior is to block only those overrides, retain native tools, surface a bounded diagnostic, and resume ownership after valid settings plus `/reload`.
- The exact theme values and spinner frame sequence may change during the first visual fixture review, but the standard-token-only rule, fixed visual width, status meanings, breakpoints, and output budgets are fixed and may not be reopened during implementation.
- The public adapter's bounded queue retains explicitly decorated tool-definition objects until a matching runtime loads or the process exits. The 128-entry ceiling, version partitioning, descriptor-only metadata, drain tests, and descriptor restoration keep this load-order mechanism bounded; it must never grow through automatic tool scanning.
